## Setup Instructions

### 1. Create Build and Deploy Workflow
This Jekyll static site requires building before testing. Create `.github/workflows/build-and-deploy.yml`:
- Installs Ruby and Jekyll dependencies
- Builds the Jekyll site with `bundle exec jekyll build`
- Deploys to GitHub Pages
- Outputs the GitHub Pages URL as `deployment_url`
- Workflow name MUST be "Build and Deploy" for workflow chaining

### 2. Workflow Chaining Architecture
The workflows are chained in this order:
1. **Build and Deploy** workflow runs first (on push/PR)
2. **Generate TestDriver Tests** workflow runs after build completes (via `workflow_run` trigger)
3. **TestDriver Tests** workflow runs after build completes (via `workflow_run` trigger)

Both TestDriver workflows use `workflow_run` with `workflows: ["Build and Deploy"]` to ensure they only run after successful build and deployment.

### 3. Deployment URL Flow
- Build workflow outputs: `https://square.github.io` (the GitHub Pages URL)
- Both TestDriver workflows receive this URL in their "Get deployment URL" step
- URL is passed to TestDriver via `TD_WEBSITE` environment variable
- Lifecycle files reference `${TD_WEBSITE}` to navigate to the deployed site

### 4. Environment Variables
Set these secrets in GitHub repository settings:
- `TD_API_KEY`: Your TestDriver API key from dashboard

The `TD_WEBSITE` variable is automatically set by the workflows to the GitHub Pages URL.

### 5. Generate Tests
The Generate workflow will automatically:
- Run after successful build and deployment
- Generate 5 exploratory tests for the web app
- Commit generated tests back to the branch
- Can also be triggered manually via workflow_dispatch

### 6. File Structure
Create these files:
```
.github/workflows/
  ├── build-and-deploy.yml (builds Jekyll site, deploys to GitHub Pages)
  ├── testdriver.yml (runs tests after build)
  └── generate-tests.yml (generates tests after build)
testdriver/
  └── lifecycle/
      └── provision.yaml (launches browser to deployed site)
```

## Rationale

This approach is recommended for the Square Open Source Portal because:

1. **Jekyll Requires Build Step**: The project uses Jekyll (evident from `_config.yml`, `Gemfile`, and `bundle exec jekyll serve` in README), which requires building the static site before it can be tested. The source files must be compiled into the `_site` directory.

2. **GitHub Pages Deployment**: The existing `.travis-ci.org` setup suggests this was previously deployed via CI/CD. The build workflow deploys to GitHub Pages at `https://square.github.io`, which is the canonical URL for Square's open source portal.

3. **Workflow Chaining via workflow_run**: 
   - The `workflow_run` trigger ensures TestDriver tests only run after successful build and deployment
   - This prevents tests from running against stale or non-existent deployments
   - Both generate and test workflows depend on the build workflow completing

4. **Separation of Concerns**:
   - **Build Workflow**: Handles Ruby/Jekyll setup, dependency installation, site building, and GitHub Pages deployment
   - **Generate Workflow**: Creates exploratory tests after deployment is ready, commits them back to the repo
   - **Test Workflow**: Executes tests against the live deployed site
   - **Lifecycle Files**: Only launch browser and navigate to the deployed URL

5. **No Building in Lifecycle Files**: The provision.yaml file only launches Chrome and navigates to the pre-deployed GitHub Pages URL. All building and deployment happens in the Build workflow.

6. **Testing Focus Areas**: The portal displays repository information from GitHub API, includes custom styling, rotated images, and responsive design - all of which can be effectively tested with TestDriver's exploratory and regression tests.

7. **Auto-generation of Tests**: The generate workflow automatically creates tests and commits them, streamlining the test creation process for this static site showcase.
