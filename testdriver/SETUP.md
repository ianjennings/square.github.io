# TestDriver Setup for Square Open Source Portal

## Step 1: Build and Deploy the Jekyll Site in GitHub Actions

Create `.github/workflows/testdriver.yml`:

```yaml
name: TestDriver Tests

on:
  pull_request:
  push:
    branches: [master]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      
      - name: Setup Ruby
        uses: ruby/setup-ruby@v1
        with:
          ruby-version: '3.1'
          bundler-cache: true
      
      - name: Build Jekyll Site
        run: |
          bundle install
          bundle exec jekyll build
      
      - name: Serve Jekyll Site
        run: |
          bundle exec jekyll serve --detach --port 4000
          sleep 5
      
      - name: Run TestDriver Tests
        env:
          TESTDRIVER_API_KEY: ${{ secrets.TESTDRIVER_API_KEY }}
          TD_WEBSITE: 'http://localhost:4000'
        run: |
          npx testdriverai@latest run
```

## Step 2: Initialize TestDriver Configuration

Run in your project root:
```bash
npx testdriverai@latest init
```

When prompted, enter: `http://localhost:4000`

This creates the `testdriver/` directory structure with lifecycle files.

## Step 3: Generate Exploratory Tests

Create initial exploratory tests:
```bash
cd testdriver
npx testdriverai@latest generate web 5
```

This generates 5 exploratory test prompts for the static website.

## Step 4: Review and Convert to Regression Tests

Review the generated tests in `testdriver/tests/` and convert promising ones:
```bash
npx testdriverai@latest run --write
```

## Step 5: Add TestDriver API Key to GitHub Secrets

1. Go to your repository Settings → Secrets and variables → Actions
2. Add `TESTDRIVER_API_KEY` with your key from https://testdriver.ai

## Step 6: Commit and Push

```bash
git add .github/workflows/testdriver.yml testdriver/
git commit -m "Add TestDriver automated testing"
git push
```

Tests will now run automatically on pull requests and pushes to master.

## Rationale

This approach is recommended because:

1. **Static Jekyll Site Architecture**: The project uses Jekyll to generate static HTML files. The build process (`bundle exec jekyll build`) must happen in CI/CD before TestDriver runs, as lifecycle files cannot and should not handle build processes.

2. **Existing Travis CI Pattern**: The repo already uses Travis CI (.travis.yml exists), indicating the team is familiar with CI/CD patterns. We extend this to GitHub Actions with proper build-then-test workflow.

3. **Local Development Server**: Jekyll's built-in server (`jekyll serve`) provides a simple way to host the static files during testing without requiring deployment to external hosting.

4. **Separation of Concerns**: 
   - GitHub Actions handles: Installing Ruby, installing dependencies, building Jekyll site, starting server
   - TestDriver handles: Launching browser, navigating to site, running tests
   - This follows TestDriver best practices where lifecycle files ONLY interact with pre-built applications

5. **Environment Variable Pattern**: Using `TD_WEBSITE` environment variable allows flexibility - tests can run against localhost:4000 in CI, or against the production https://square.github.io site by simply changing the variable.

6. **Exploratory Test Generation**: The `generate web 5` command will create tests that explore repository listings, navigation, responsive behavior, and link functionality - all critical for an open source portal.

7. **No Build Logic in Lifecycle Files**: The provision.yaml strictly follows the rule of NOT building anything - it only launches Chrome to the URL where the app is already running, which was started by GitHub Actions.
