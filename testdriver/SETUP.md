# TestDriver Setup for Square Open Source Portal

## Overview
This is a Jekyll static site that requires building before testing. We'll create two workflows:
1. **Build & Deploy Workflow**: Builds Jekyll site and deploys to GitHub Pages, outputs the deployment URL
2. **TestDriver Workflow**: Depends on build workflow, receives URL, and runs tests

## Step-by-Step Setup

### 1. Create Build & Deploy Workflow
Create `.github/workflows/build-and-deploy.yml`:
- Installs Ruby and Jekyll dependencies (bundler)
- Runs `bundle exec jekyll build` to generate static site
- Deploys to GitHub Pages
- Outputs deployment URL as `deployment_url`

### 2. Create TestDriver Workflow
Create `.github/workflows/testdriver.yml`:
- Uses `needs: build` to depend on build-and-deploy job
- Receives `deployment_url` from build workflow via `needs.build.outputs.deployment_url`
- Sets `TD_WEBSITE` environment variable with the deployment URL
- Runs TestDriver lifecycle files and tests

### 3. Create Lifecycle Files
Create `testdriver/lifecycle/provision.yaml`:
- Launches Chrome browser
- Navigates to `${TD_WEBSITE}` (the pre-built GitHub Pages URL)
- Waits for page to load
- **Does NOT build Jekyll** - that's already done in the build workflow

### 4. Environment Variables
- `TD_WEBSITE`: Set automatically by TestDriver workflow from build output
- `TD_API_KEY`: Add to repository secrets (Settings → Secrets → Actions → New repository secret)

### 5. Generate Tests
Run: `npx testdriverai@latest generate web 3`
This creates 3 exploratory tests in `testdriver/generate/` that will test the portal

### 6. Trigger
Push changes to trigger both workflows. Build workflow runs first, then TestDriver workflow uses the deployed URL.

## Rationale

This is a Jekyll-based static site that REQUIRES a build step before testing. Evidence:

1. **Jekyll Site Detection**: The repository contains `_config.yml` and `Gemfile` with Jekyll dependencies, and the README explicitly shows `bundle exec jekyll serve` for local development.

2. **Why Build Workflow is Needed**: 
   - Jekyll sites must be compiled from source files (markdown, templates) into static HTML
   - The site cannot be tested in its raw form - it needs to be built and served
   - The existing `.travis-ci.yml` shows CI was used historically, but we need modern GitHub Actions

3. **Architecture Choice**:
   - **Build Workflow**: Builds Jekyll site and deploys to GitHub Pages (the natural deployment target for this repo since it's square.github.io)
   - **TestDriver Workflow**: Triggered after build completes, receives the GitHub Pages URL, and tests the deployed site
   - **Lifecycle Files**: Only launch Chrome and navigate to the deployed URL - NO building

4. **URL Handling**: 
   - Build workflow outputs the GitHub Pages URL from the deploy action
   - TestDriver workflow constructs URL from repo name if direct output isn't available
   - For square.github.io, the URL is https://square.github.io

5. **No Building in Lifecycle**: The provision.yaml ONLY launches Chrome with TD_WEBSITE - the site is already built and deployed by the time TestDriver runs.

This separation ensures proper CI/CD flow: Build → Deploy → Test, with each stage responsible for its specific task.
