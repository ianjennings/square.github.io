# TestDriver Setup for Square Open Source Portal

## Prerequisites
- TestDriver CLI installed: `npm install -g testdriverai`
- GitHub repository access

## Step 1: GitHub Actions Workflow (Build & Deploy)

Create `.github/workflows/testdriver.yml`:

```yaml
name: TestDriver Tests

on:
  push:
    branches: [master]
  pull_request:
    branches: [master]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      
      # Build the Jekyll site
      - name: Setup Ruby
        uses: ruby/setup-ruby@v1
        with:
          ruby-version: '2.7'
          bundler-cache: true
      
      - name: Install dependencies
        run: |
          gem install bundler
          bundle install
      
      - name: Build Jekyll site
        run: bundle exec jekyll build
      
      # Serve the built site
      - name: Serve Jekyll site
        run: |
          bundle exec jekyll serve --detach --port 4000
          sleep 5
        
      # Run TestDriver tests
      - name: Run TestDriver Tests
        env:
          TD_WEBSITE: http://localhost:4000
          TESTDRIVER_API_KEY: ${{ secrets.TESTDRIVER_API_KEY }}
        run: |
          npx testdriverai@latest init
          npx testdriverai@latest generate web 5
          npx testdriverai@latest run
```

## Step 2: Add TestDriver API Key
1. Go to your repository Settings → Secrets and variables → Actions
2. Add new secret: `TESTDRIVER_API_KEY` with your TestDriver API key

## Step 3: Initialize TestDriver

Run locally to set up configuration:
```bash
npx testdriverai@latest init
```

When prompted, enter: `http://localhost:4000`

## Step 4: Generate Exploratory Tests

Create initial exploratory tests:
```bash
export TD_WEBSITE=http://localhost:4000
npx testdriverai@latest generate web 5
```

This creates 5 exploratory test prompts that TestDriver will use to explore your site.

## Step 5: Convert to Regression Tests (Optional)

After exploratory tests run successfully, convert them to regression tests:
```bash
npx testdriverai@latest generate web 5 --write
```

## Step 6: Run Tests Locally

First, build and serve the Jekyll site:
```bash
bundle install
bundle exec jekyll serve
```

In another terminal, run TestDriver:
```bash
export TD_WEBSITE=http://localhost:4000
npx testdriverai@latest run
```

## Environment Variables
- `TD_WEBSITE`: The URL where the Jekyll site is served (http://localhost:4000 locally, or your production URL)
- `TESTDRIVER_API_KEY`: Your TestDriver API key for authentication

## Testing Staging/Production

For testing the live site at https://square.github.io:
```bash
export TD_WEBSITE=https://square.github.io
npx testdriverai@latest run
```

## Rationale

This approach is ideal for the Square Open Source Portal because:

1. **Static Jekyll Site**: The repository uses Jekyll to generate a static site, which needs to be built before testing. The GitHub Actions workflow handles this build step.

2. **Existing Build Process**: The README shows the site uses `bundle exec jekyll serve` for local development. We replicate this in CI/CD, ensuring the site is built and served before TestDriver runs.

3. **Separation of Concerns**: 
   - GitHub Actions: Builds Jekyll site, installs Ruby/Bundler dependencies, serves the site
   - TestDriver Lifecycle Files: Only launches browser and navigates to the pre-built site
   - This follows TestDriver best practices by not mixing build and test concerns

4. **Travis CI Migration**: The repo currently uses Travis CI (.travis.yml), but we provide a modern GitHub Actions workflow that can replace it while adding TestDriver testing.

5. **Environment Variable Pattern**: Using `TD_WEBSITE` allows the same test configuration to work for:
   - Local development (http://localhost:4000)
   - Staging environments
   - Production (https://square.github.io)

6. **Dynamic Content**: Since the site generates content from repos.json and GitHub API, exploratory tests can verify that repository cards, images, and links are properly rendered.

7. **Simple Lifecycle**: The provision.yaml simply launches Chrome to the URL - no complex setup needed since it's a static site with no authentication or database requirements.
